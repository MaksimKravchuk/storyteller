# Spec-Driven Development with GitHub Spec Kit

Date: 2026-06-30 (bounded iteration added 2026-09-30)
Status: Active workflow
Related: `docs/decisions/0017-adopt-spec-kit-as-requirements-layer.md`, `.specify/memory/constitution.md`

## Why this exists

Storyteller already uses strict PR, ADR, benchmark, and review gates. The missing layer was a durable place to record the intent of non-trivial features before an agent starts coding. GitHub Spec Kit fills that gap by creating repo-tracked requirements, plans, checklists, and task lists.

Spec Kit is not a replacement for Storyteller's engineering workflow. It is the intake and planning layer before implementation.

## Installed artifacts

```text
.specify/
├── memory/constitution.md       # Storyteller principles for Spec Kit flows
├── scripts/bash/                # Spec Kit helper scripts
├── templates/                   # Spec, plan, task, checklist templates
└── workflows/speckit/           # Bundled workflow metadata

.claude/skills/speckit-*/        # Claude Code skills generated by Spec Kit
```

The project was initialized with:

```bash
uvx --from git+https://github.com/github/spec-kit.git specify init . \
  --integration claude \
  --script sh \
  --ignore-agent-tools
```

Persistent installation, when desired:

```bash
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@vX.Y.Z
specify version
```

Use a real release tag from <https://github.com/github/spec-kit/releases> instead of `vX.Y.Z`.

## Default Storyteller flow

Pick the smallest flow that fits (see constitution "Spec-Driven Workflow"):

| Work size | Flow |
| --- | --- |
| Small: one module, obvious behavior, typo, narrow bug fix | No Spec Kit. Follow `CLAUDE.md` directly. |
| Medium: clear intent, several files | `/speckit-specify` → `/speckit-plan` → `/speckit-tasks` |
| Large or risky: prompts/agents, persistence, player-facing behavior, several modules | `/speckit-specify` → `/speckit-clarify` (only if blocking unknowns) → `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze` (one pass) |

`/speckit-checklist` and `/speckit-converge` are opt-in: only when Max asks or the plan names a specific high-risk domain.

Then implement through the normal Storyteller path:

```text
Hermes scopes from spec -> Claude Code writes surgical changes -> Hermes inspects diff -> deterministic verification -> PR
```

`/speckit-implement` is optional. Do not use it as the default autopilot for Storyteller unless the task is narrow, the generated tasks are already reviewed, and the implementation permissions are scoped.

## Stop rules: resolve contradictions, do not polish forever

Spec Kit's generic commands happily produce more questions, more checklist items, more findings, and more tasks on every run. Left unchecked, an agent loops `analyze → edit → analyze` and the feature grows with each pass. Storyteller bounds this with constitution Principle VI:

1. **Only blocking findings get fixed.** Blocking means one of: a contradiction between artifacts/ADRs/constitution; a guardrail (constitution MUST or accepted ADR) violation; a P1 story or requirement with no task; a load-bearing unknown (changes player-visible behavior, persisted data, security/privacy, or paid cost, with no safe default). Everything else is a one-line "Known gap".
2. **One round, then escalate.** Each command runs once. Blocking findings get one targeted remediation pass and one re-check of just those findings. Still blocking → stop and ask Max with 2–3 options. No third round.
3. **Remediation never adds scope.** Fixes may clarify, reconcile, delete, or down-prioritize. New stories, requirements, success criteria, and tasks are not allowed (except the minimum task to cover an existing P1 requirement). New ideas go to the spec's "Out of Scope / Follow-ups" section.
4. **Done means "no blocking findings", not "every box checked".** Unchecked checklist items do not block implementation.
5. **Big specs get split, not expanded.** Beyond roughly 3 user stories or 10 functional requirements, split into separate features.

Local overrides in the generated `speckit-*` skills are marked "Storyteller override" so they can be re-applied after a Spec Kit upgrade.

## When to use Spec Kit

| Work type | Use Spec Kit? | Notes |
| --- | --- | --- |
| New gameplay capability | Yes | Capture user stories, edge cases, narrative evidence. |
| Prompt or agent-role changes | Yes | Also inspect ADRs and consider a new ADR. |
| Web/admin UX feature | Yes | Include demo/screenshot evidence in quickstart or PR. |
| Persistence or schema behavior | Yes | Include migration/rollback and consumer-seam verification. |
| Benchmark/scenario additions | Yes | Define expected rubric/evidence before coding. |
| Small typo/docs fix | No | Direct docs PR is enough. |
| Narrow bug fix with obvious regression test | No | Use strict TDD directly. |
| Emergency production fix | Optional after fix | Backfill a spec/ADR if the decision must survive. |

## Feature artifact expectations

A completed Spec Kit planning pass should leave a feature directory under `specs/` with some or all of:

```text
specs/NNN-short-name/
├── spec.md
├── plan.md
├── research.md
├── data-model.md
├── quickstart.md
├── contracts/
├── checklists/
└── tasks.md
```

For Storyteller, make these concrete:

- `spec.md`: player/founder/operator value, prioritized user stories, acceptance scenarios, success criteria.
- `plan.md`: touched modules, ADRs inspected, quality gates, benchmark/e2e approval state, implementation approach.
- `research.md`: targeted answers only; avoid broad background research.
- `quickstart.md`: the exact smoke/demo/test path that proves the feature.
- `tasks.md`: small implementation tasks that can map to Claude/Hermes work chunks or PR checklist items.

## Required Storyteller checks inside a plan

Every `plan.md` should answer these before coding starts:

1. **Decision records**: Which accepted ADRs or `docs/studio/09-founder-decision-register.md` entries apply?
2. **New ADR needed?** Required for significant architecture, agent-role, prompt-boundary, persistence, release, or player-facing decisions.
3. **Consumer seam**: Where does the final consumer receive the value, and how will we prove it?
4. **Locale parity**: If touching prompts, are English and Russian prompt variants both in scope?
5. **Paid evidence**: Does this need e2e or benchmark runs? If yes, has Max approved the cost?
6. **Demo contract**: What PR evidence is enough for the touched surface?

## Example prompts

Create a new feature spec:

```text
/speckit-specify Add a friends-beta onboarding flow that lets approved beta users sign in, see their quota, and submit structured feedback after a session.
```

Clarify risk areas before planning:

```text
/speckit-clarify Focus on auth boundaries, quota visibility, feedback privacy, and what evidence is required before beta release.
```

Plan with Storyteller context:

```text
/speckit-plan Use the existing FastAPI web UI and async SQLAlchemy persistence. Follow CLAUDE.md, inspect docs/decisions and the founder decision register, avoid paid e2e unless explicitly approved, and define consumer-seam tests.
```

Break down and analyze before coding (analyze reports blocking contradictions only):

```text
/speckit-tasks
/speckit-analyze
```

## PR expectations

PRs produced from a Spec Kit flow should link the spec artifacts in the body:

```md
## Spec Kit
- Spec: `specs/NNN-short-name/spec.md`
- Plan: `specs/NNN-short-name/plan.md`
- Tasks: `specs/NNN-short-name/tasks.md`

## Test evidence
- ...
```

Docs-only Spec Kit workflow changes do not require full app benchmarks. Code or prompt changes still follow the normal Storyteller quality gates.

## Maintenance

- Keep `.specify/memory/constitution.md` aligned with `CLAUDE.md`, `AGENTS.md`, and accepted ADRs.
- When Spec Kit changes generated skill names or workflow semantics, update this document and the agent guidance.
- Do not store credentials or private local state in `.claude/` or `.specify/`.
- Review generated skills before upgrading Spec Kit in the repo, and re-apply the sections marked "Storyteller override" (bounded iteration) in `speckit-specify`, `speckit-clarify`, `speckit-checklist`, `speckit-tasks`, `speckit-analyze`, `speckit-converge`, and `speckit-implement`, plus the trimmed Polish phase in `.specify/templates/tasks-template.md`, the Principle VI line in the Constitution Check of `.specify/templates/plan-template.md`, and the "Out of Scope / Follow-ups" section in `.specify/templates/spec-template.md`.
